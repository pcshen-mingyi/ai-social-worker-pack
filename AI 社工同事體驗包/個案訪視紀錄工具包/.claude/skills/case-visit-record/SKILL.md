# 個案訪視紀錄

把一次家訪的逐字稿/筆記，轉成明怡個案紀錄表格式的 docx 檔案。

## 使用時機

- 使用者貼上家訪逐字稿或筆記，或提供案號（例如 CASE-001），要求整理訪視紀錄
- 使用者說「幫我整理這次的訪視紀錄」「這是今天的家訪逐字稿」等

如果使用者沒有提供案號，先問清楚案號，再繼續。

## 流程

> 下面指令裡的 `scripts/`、`data/`、`templates/` 都是相對於**這個 skill 資料夾**
> （也就是這份 SKILL.md 所在目錄）的路徑，執行時請換成完整路徑，例如
> `node <skill 目錄>/scripts/fill_identity.mjs`。

## 設定

`shared/config.json` 已經預先填好體驗用的設定（個案資料表路徑、草稿資料夾等），
不需要另外設定就能直接體驗。下面步驟 1 的輸出位置、步驟 2 的 `--data`
都直接讀這份設定。

### -1. 環境檢查（不需要了）

這一版不需要安裝任何東西，也沒有環境檢查步驟。

腳本改用 Node.js 寫成，而 Claude Code 本身就帶 Node；讀字型與繪圖用的
程式碼和字型檔都在 `shared/vendor/`、`shared/assets/` 裡。
**不要**去跑 pip、npm 或任何安裝指令，也不要問使用者要不要安裝。

### 0. 找逐字稿（如果使用者沒有直接貼文字）

如果使用者只給了案號、沒有直接貼逐字稿文字，先去 `shared/config.json` 的
`raw_transcript_dir`（`個人工作/訪視原始資料/`）底下找檔名包含該案號的逐字稿檔案，
讀取內容當作後續步驟的輸入。找不到對應檔案時，跟使用者確認案號或請對方直接貼上逐字稿。

### 1. 複製範本

把 `templates/明怡個案紀錄表-demo版.docx` 複製一份到 `shared/config.json` 的
`draft_dir`（尚未核准的草稿都放這裡），檔名建議 `{案號}_訪視紀錄_{日期}.docx`，
**日期一律用 `YYYYMMDD`（例如 `20260804`），不要用含 `/` 的格式**——`/` 是路徑
分隔符號，放進檔名會存錯位置或直接失敗，之後 `case-visit-approval` 歸檔時
也是統一用這個格式對應。**不要直接修改範本檔本身。**

### 2. 填身分欄位（不經過你）

呼叫 `scripts/fill_identity.mjs`：

```bash
node scripts/fill_identity.mjs --case-id CASE-001 \
  --data {shared/config.json 的 case_data_xlsx} \
  --docx 輸出檔.docx \
  --out 輸出檔.docx
```

這支腳本會自己讀 Excel、比對案號、寫入姓名／身分證字號／電話／地址等身分欄位。
**你只會看到「已成功寫入」的訊息，看不到實際欄位內容**——這是刻意設計，身分資料不應該
出現在對話紀錄裡。如果案號不存在，腳本會回報錯誤，這時候跟使用者確認案號是否正確。

### 3. 從逐字稿草擬敘事內容

讀使用者提供的逐字稿/筆記，依序完成下面三層，**一層接著一層推導，不要各自獨立填寫**
（結構見 `references/template-structure.md`）：

**3-1　主述議題／個案概況**

從逐字稿摘要案主的求助問題、家庭狀況、子女情形。這一層是事實整理，忠於逐字稿內容。

**3-2　各項評估（要有專業判斷邏輯，不是逐字稿摘要）**

針對逐字稿有提到的面向（生活自理與日常功能、醫療與復健需求、居家與無障礙環境、
就學／就業與社會參與、家庭支持與照顧者負荷、經濟與福利資源使用——可視個案增減），
每一項都要做到「事實 → 專業判斷」，例如：

- 不是只寫「案主表示行動不便，需要輪椅」，而是要接著判斷：這對日常生活自理造成
  什麼影響？現有居家環境／照顧人力足以因應嗎？風險等級如何？
- 不是只寫「案主獨居」，而是要判斷：獨居搭配目前的健康/經濟狀況，照顧空窗風險
  高不高？是否有立即需要介入的安全疑慮？

沒有足夠資訊做判斷的面向，誠實寫「（逐字稿資訊不足，待下次訪視或家訪確認）」，
不要為了填滿欄位而杜撰專業判斷。

**3-3　需求評估**

綜合 3-2 每一項評估的判斷，整合出案主目前最核心、最優先的 1–3 個需求。
這一層是從 3-2 的結論「收斂」出來的，不要引入 3-2 沒談到的新事實。

**3-4　處遇計畫建議（必須從 3-2／3-3 的結論推導，不是獨立發想）**

處遇計畫的每一條建議都要能回答「這是在回應哪一項評估／需求？」：

- 短期目標與行動（1–3 個月）：對應 3-3 裡最急迫的需求
- 中長期目標與行動：對應 3-3 裡需要持續介入、非短期能解決的需求
- 轉介／資源連結建議：對應 3-2 裡發現案家自身資源不足以因應的部分
- 下次追蹤時間：依風險等級決定（風險越高、間隔應越短），不是隨意填一個月份

如果某一條計畫建議在 3-2/3-3 找不到對應的評估依據，代表這條建議不該出現——先回頭
補齊評估，不要跳過評估直接生建議。

**每個類別裡如果有超過一項行動，一定要標示優先順序**（依風險急迫性排列，
最急迫的排第一），不要用「、」「；」平鋪並列、看不出先後——這是主管審核時
最常挑的問題。格式範例（每項前面標數字＋一句話講為什麼是這個順序）：

```
1. 協助申請交通接送服務（優先：目前回診中斷風險最高，直接影響心臟/血糖追蹤）
2. 安排居家無障礙環境評估（次要：跌倒風險偏高但案主目前尚能自理，急迫度略低於就醫）
3. 協助申請送餐服務（第三：營養/體重問題已持續半年，非立即危險，但需要開始介入）
```

**寫入 docx**

把 3-1～3-4 的內容整理成 JSON 檔（欄位名稱見 `scripts/fill_narrative.mjs` 開頭的說明），
然後呼叫：

```bash
node scripts/fill_narrative.mjs --docx 輸出檔.docx --out 輸出檔.docx --json 欄位.json
```

這些內容本來就來自逐字稿本身，不像身分欄位需要保密，所以由你直接草擬即可。**誠實原則**：
逐字稿裡如果提到案主或家人的真實姓名，敘事文字裡還是會照實出現——這支腳本解決的是
「身分欄位不必經過你去猜」，不是整份文件的去識別化。如有不確定或逐字稿沒提到的欄位，
留白或標註「（訪視當日未提及，待補充）」，不要杜撰內容。

### 4. 接著執行家系圖

訪視紀錄敘事內容寫入 docx 後，**立刻接續使用 `case-genogram` skill**，
把畫好的家系圖 PNG 嵌入同一份 docx 的「家系圖」區塊，不需要使用者另外開口要求。
兩件事都完成，才算是本次訪視紀錄產出完畢。

### 5. 完成後

告訴使用者輸出檔案的路徑，並提醒：這是 demo 簡化版範本，不影響機構正式表單。
請使用者親自檢查一次內容（尤其是 3-2～3-4 的專業判斷是否合理）。
確認無誤後，接著使用 `case-visit-approval` skill 寄給主管確認歸檔。
如果主管退件要求修改，回到本步驟（3）依意見調整，改完後重新執行步驟 4（家系圖）
並重新走一次 `case-visit-approval` 流程。
