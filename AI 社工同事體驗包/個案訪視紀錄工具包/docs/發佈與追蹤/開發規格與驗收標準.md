## 0. 一頁摘要

**現況缺什麼**：工具包只能靠人工複製資料夾分享，沒有下載連結；用了之後有多少人真的下載、真的打開、真的走完流程，完全不知道。

**這版補什麼**：
1. 打包成可從 GitHub Release 下載的 zip，連結永遠指向最新版（比照小白包）。
2. 加入靜默、匿名的「啟用」與「完成體驗」兩筆事件回報，寫進 **MYmate 小白包同一份統計試算表**裡新增的分頁與趨勢表。
3. **比照小白包目前的做法**，同步做「下載數」追蹤（每日抓 GitHub Release 的下載次數），組成「下載 → 啟用 → 完成」的漏斗，而不是只有裸的兩個事件計數。

**北極星（做完之後，什麼事會發生）**：培力部門同事把下載連結貼給學員，不用口頭教任何安裝步驟；PC／培力部門打開同一份統計試算表，就能看到「下載數」「啟用數」「完成數」「啟用率」「完成率」隨時間的走勢，不用另外問學員或翻信箱回報。

**前提**：
- 這是 PC 主動決定「跟小白包共用同一份試算表」，不是這次任務自行假設沿用——落地時會直接修改 **MYmate 專案既有、正在跑的** Apps Script 後端與部署，這是刻意的共用決定，需要在改動前後都跟 MYmate 那邊的維護文件同步，也要保證小白包既有資料完全不受影響。
- 這個工具包本身**沒有「動到全機設定」的安裝步驟**（不像小白包的 `install.mjs` 會複製東西到 `~/.claude`），所以不套用小白包 install/uninstall 那套邏輯，只做「事件回報」等級的東西。
- 對象是社工，不是工程師：能自動偵測的事件盡量自動偵測，不要求使用者多做任何操作；回報失敗一律吞掉，永遠不影響體驗本身。
- demo 內容（逐字稿、個案資料表）全部是假資料，這次改動不牽涉任何真實個資，也不新增任何會摸到真實個資的邏輯。
- **小白包的統計後端一直在持續優化**（v1.9 匿名計數 → v2.0 後端上線並修掉數字格式/趨勢兩個 bug → 現在又加了下載追蹤），這次要做的是「跟上目前最新的那一版設計」，不是複製一個舊版本的做法。

## M1：打包與發布（GitHub Release）

- 建一個新的公開 repo（暫定名稱 `mingyi-case-visit-kit`，PC 可改），內容結構為目前的三個資料夾（`個案訪視紀錄工具包/`、`明怡服務紀錄資料夾/`、`個人工作/`）在同一層。
- **打包時就把三者放在 zip 的同一層**，解壓縮後不需要使用者再手動搬移——這是可以順便做的體驗優化，跟「發布」本身直接相關，納入這個里程碑。
- 固定 zip 檔名（比照小白包 `MYmate-starter-kit.zip` 的模式），下載連結固定指向 `releases/latest`，之後發新版不用重發連結。
- **打包一定要用會設定 UTF-8 檔名旗標的工具（例如 Python `zipfile` 模組），不要用 macOS 內建的 `zip` 指令**——這個工具包路徑幾乎全是中文（`個案訪視紀錄工具包/`、`明怡服務紀錄資料夾/`、`個人工作/`…），macOS `zip`（Info-Zip 3.0）預設不會設這個旗標，Windows 內建解壓縮就會用錯編碼解檔名、直接解壓縮失敗。v1.0／v1.1 剛發布時都踩過這個坑，詳見專案卡 2026-08-20 紀錄。
- README／CLAUDE.md 加一個版本號欄位供回報使用（比照小白包 `BUNDLE_VERSION`）。

## M2：靜默回報「啟用」事件

- 新增 `shared/scripts/_stats.mjs`，**逐行比照小白包目前的 `_stats.mjs`**（不要只看設計理念、要照抄實作細節），包含：
  - `STATS_ENDPOINT`：與小白包**同一個** Apps Script `/exec` 網址
  - `PRODUCT_ID = "case-visit-kit"`
  - `KIT_VERSION`（對應 M1 的版本號）
  - **AbortController + 2000ms timeout**：逾時或任何錯誤一律吞掉回傳 `false`，永不拋錯、永不阻塞（小白包已用真實測試證明「端點不通時延遲增加 0 秒」，這支要一樣）
  - `statsEnabled()`：`Boolean(STATS_ENDPOINT) && process.env.MYMATE_NO_STATS !== "1"`（沿用同一個環境變數，不要另外發明）
  - `statsNotice()`：給使用者看的一句話說明——**這個包沒有小白包那種「跑完 install.mjs 印一段訊息」的天然時機**，所以改成：第一次啟用回報成功後，由 Claude 在**當次對話的第一句回覆**裡帶一句話告知（例如「（已回報一筆匿名使用計數，只有事件/版本/系統，不含任何個資；不想回報可設定 `MYMATE_NO_STATS=1`）」），不要藏在文件裡才提一次——這是延續小白包「說什麼寫在三個地方一致（程式碼註解／README／使用當下）」的原則，只是把「使用當下」的呈現方式換成對話而不是終端機輸出。
- 用 `.claude/hooks/` 底下一個 SessionStart hook，偵測「這份資料夾是不是第一次在這台機器上啟動」：用本地標記檔（例如 `shared/.state/activated.json`）判斷，沒有標記檔才送出事件並建立標記檔，避免同一次安裝反覆開啟 Claude Code 就一直重複回報。
- 送出內容只有 `{event:"activate", version, platform, product:"case-visit-kit"}` 四個欄位，不帶任何識別碼、路徑、檔名、逐字稿或個案資料內容。
- `--dry-run` 等價情境（若這個工具包未來加類似 dry-run 的測試模式）不送出任何東西——目前沒有這個模式就不用特別做，但邏輯要留可以插入的空間。

## M3：偵測並回報「完成體驗」事件

- 定義「完成體驗」＝ `case-external-record-entry` skill 執行到「表單填完、截圖給使用者看、等待使用者自己按提交」這一步——這是 Claude 這端能確實知道自己做完的最後一步。**這是代理指標，不是「使用者真的按下瀏覽器提交鍵」的技術確認**，規格與文件都要講清楚這一點，不要讓人誤以為是精確的轉換率。
- 用同一支 `_stats.mjs` 送出 `{event:"complete", version, platform, product:"case-visit-kit"}`，一樣靜默、失敗吞掉、可用同一個環境變數關閉。
- 同一份體驗跑第二次（例如同一人先後試了 CASE-001 跟 CASE-006）重複回報視為合理，不特別去重——比照小白包「這是次數不是人數」的哲學。

## M4：後端——同一份試算表新增分頁、趨勢表，並接上下載數追蹤

### M4a：事件計數分頁（比照小白包目前的 doPost 寫法）

- 修改 MYmate 小白包現有的 Apps Script（`.../MYmate-小白包/backend/程式碼.js`）：
  - `doPost` 依 payload 的 `product` 欄位路由：**沒有 `product` 欄位或值為預設值時，維持寫入既有「小白包」分頁、既有欄位順序不變**（保證小白包既有用戶端、既有資料完全不受影響）；`product === "case-visit-kit"` 時寫入新分頁「個案訪視工具包」。
  - **比照小白包目前已經做的三個硬化措施，這裡也要有**：
    1. `event` 白名單——只接受 `"activate"`／`"complete"`，其餘一律丟棄（`return ok()`，不寫入）。
    2. `version`／`platform` 一律 `.slice(0, 20)` 截斷。
    3. **不寫入 IP、User-Agent，或請求裡任何其他欄位**；任何解析／寫入錯誤一律 `catch` 後仍回 200（`ok()`），不對外洩漏內部狀態。
  - 寫入時**版本與平台一律用 `setNumberFormats("@")` 存成文字**（比照小白包 `writeRow()`，避免 `"2.0"` 被試算表自動判成數字 `2`、`"2.10"` 跟 `"2.1"` 撞值的 bug）。
- 新增一個對應「個案訪視工具包-統計」分頁（儀表板），結構比照小白包目前的「統計」分頁：
  - 說明列（「這是次數不是人數」等前提）放最上面
  - 即時快照（啟用累計、完成累計、完成率——**不要用「淨留存」這個詞，啟用跟完成不是相反動作，沒有淨留存的概念**）
  - 每日趨勢：**用連續日期軸＋逐日 `COUNTIFS`**，不要用 `QUERY ... group by toDate()`（小白包 v2.0 才修掉這個 bug——沒有事件的日子必須補 0，否則曲線會誤導判讀）
  - 每週彙總（近 12 週，比照小白包 `WEEKLY_WEEKS`）
  - 版本／平台分布（`distFormula` 那種寫法，空資料要顯示「（還沒有資料）」，不能用 `IFERROR` 防空狀態——`COUNTA` 判斷有沒有資料才是對的做法，小白包的註解已經解釋過原因，照做）

### M4b：下載數追蹤（比照小白包目前已經加上的「下載」分頁機制）

- 小白包的後端**已經**多了一段「下載追蹤」：每天抓一次 GitHub Release 的累計下載數，寫進獨立的「下載」分頁，並用這個數字組出「下載 → 安裝 → 卸載」的漏斗（安裝率、卸載率）。這個包也要有對應版本：「下載 → 啟用 → 完成」，啟用率＝啟用÷下載、完成率＝完成÷啟用。
- **不要複製一份幾乎一樣的 `fetchDownloads()`／`downloadSheet()`／`setupTrigger()` 出來給第二個產品用**——現有這組函式目前是綁死小白包那個 repo（`GITHUB_RELEASES_API` 是常數）。請把它們**參數化**（repo 路徑、目標分頁名稱），讓同一組邏輯可以服務多個產品；每日觸發器可以是「一個 trigger 迴圈跑過所有已設定的產品」，或「每個產品各自一個 trigger、都呼叫同一支參數化函式」——哪種寫法乾淨由你判斷，但**不要貼兩份幾乎相同的程式碼**。
- 案訪視工具包的下載分頁另外命名（例如「個案訪視工具包-下載」），**小白包既有的「下載」分頁名稱與內容不要動、不要重新命名**——避免既有的公式、圖表、觸發器因為改名而全部要重接。
- 漏斗與判讀說明比照小白包現有寫法一併搬過來：
  - 下載含爬蟲，爬蟲不會啟用，所以啟用率會系統性偏低
  - 啟用是即時寫入、下載是每天才抓一次，剛發新版的頭一兩天啟用率可能反而虛高（分母比分子舊）
  - 這兩個判讀提醒**一定要照抄到新分頁**，不要因為是新分頁就省略——小白包當初把這段判讀寫進儀表板，就是為了不讓看數字的人被絕對百分比誤導。

## 5. 驗收標準（AC）

- [ ] 下載連結是 GitHub Release「最新版本」連結；解壓縮後**不需要**使用者手動搬移三個資料夾就能直接使用
- [ ] 第一次在資料夾內開 Claude Code、觸發 SessionStart hook 後，統計試算表的「個案訪視工具包」分頁多一列 `event=activate`，且該次對話的第一句回覆裡有提到已回報匿名計數與關閉方式

- [ ] 走到 `case-external-record-entry` 的截圖等待步驟後，統計試算表多一列 `event=complete`

- [ ] 「個案訪視工具包」分頁的版本／平台欄位存的是文字（不會被試算表判成數字；用 `"2.10"` 測試不會跟 `"2.1"` 撞值）

- [ ] 小白包既有的「小白包」分頁、「統計」分頁、「下載」分頁資料，在這次修改前後數字完全一致（修改前後各截一次圖或匯出 CSV 比對）

## 7. 給 Claude Code 的指引

- 開工前務必先**直接讀程式碼**，不要只看文件摘要——`.../MYmate-小白包/backend/程式碼.js` 目前的內容比 `CHANGELOG.md` 新（已經包含下載追蹤邏輯），文件可能還沒補上這段，讀程式碼本身才是準的。同時讀 `_stats.mjs`、`docs/統計設定-給維護者.md`、`CHANGELOG.md`（尤其 v1.9／v2.0 兩篇，說明了目前這些設計決定背後的理由與踩過的坑）。
- **最容易做錯的三條，先寫測試**：
  1. 「不重複回報 activate」——本地標記檔已存在時，第二次 SessionStart 不該再送出事件。
  2. 「小白包既有資料不受影響」——`doPost` 改動後，對沒有 `product` 欄位的舊格式請求（模擬小白包既有用戶端），要保證還是寫進原本的分頁、原本的欄位順序，不能因為新增分支邏輯讓舊資料錯位或重複寫入。
  3. 「下載追蹤參數化後，小白包自己的下載數還是準的」——改完 `fetchDownloads()`／`downloadSheet()` 之後，用小白包既有 repo 的資料重新跑一次，數字要跟改動前一致；再用 `mingyi-case-visit-kit` 的假資料跑一次新分頁，確認兩邊互不干擾。
- 修改正式在跑的 Apps Script 部署前，先把現有 `程式碼.js` 存一份時間戳記副本，並在 PC 確認要動手後才 `clasp redeploy`（同一個部署 ID，不要新建）。
- 全程用假資料測試，不得用任何真實個案、真實信箱測試 Gmail 相關流程。
- M1→M4 依序做，每個里程碑做完 commit＋簡短回報，等 PC 確認才進下一個。M4 拆成 M4a（事件計數）／M4b（下載追蹤）兩個子步驟分別回報也可以，下載追蹤牽涉到既有 trigger 的參數化改動，風險較高，值得單獨過一次。
